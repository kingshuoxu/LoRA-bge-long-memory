# 实验设计:基于 MoE/LoRA 专家记忆的 LLM 长记忆验证

日期:2026-07 · 状态:设计阶段,未实现

## 1. 要验证的假设

> 在冻结基座模型的前提下,通过"每批新经验 → 训练一个新的 LoRA 专家 + 门控路由决定激活",
> 可以实现可积累、可选择性读取、且不损害原有能力的长记忆。

拆成三个可证伪的子问题:

- **H1 可写入**:模型写入虚构知识后,能以高准确率回答相关提问;
- **H2 可选择性读取**:门控只在相关输入时激活对应专家,不相关输入不误触发;
- **H3 不遗忘**:顺序写入多批经验后,旧经验记忆和基座通用能力均不明显下降。

## 2. 关键设计原则:用虚构知识做测试

如果用真实事实(如"法国首都是巴黎"),无法区分"记住了"和"本来就知道"。
因此所有测试知识必须随机生成、保证基座绝不可能见过:

- 虚构实体:随机拼读的人名/公司名/地名(如 "Zorblax Industries"、"Maria Chenthorn");
- 虚构事实模板:`{实体} 的 {属性} 是 {值}`(CEO、成立年份、总部城市、产品名……);
- 每个事实配 3–5 种问法(直接问、换个句式问、干扰选项选择)。

## 3. 实验分组

| 组 | 方案 | 预期角色 |
|---|---|---|
| G1(本方案) | 冻结基座 + LoRA 专家池 + 门控路由 | 验证对象 |
| G2 | 直接 SFT 全量/LoRA 混合微调写入所有经验 | 下限对照:能记住但预期遗忘旧知识 |
| G3 | RAG(事实库存向量库,检索拼进 prompt) | 上限参照:外挂记忆的天花板 |
| G4 | 无记忆,直接提问 | 基线:预期接近 0% 准确率 |

G1 的写入/读取流程:

1. **写入**:一批虚构事实(如 50 条)作为训练文本,冻结基座,只训一组新 LoRA(注入每层 FFN),得到专家 `E_k`;
2. **路由键**:用该批事实的平均隐向量(取基座某层 hidden state 的均值)作为专家 `E_k` 的 key,存入路由表;
3. **读取**:推理时取输入在同一层的隐向量,与所有专家 key 算余弦相似度,超过阈值 τ 才加权激活对应 LoRA,否则专家完全关闭(等价于冻结基座原样输出)。

这对应论文清单里的:专家=记忆载体(Lifelong-MoE / LoRAMoE),门控=读写控制(Titans 的 surprise gate 的简化版)。

## 4. 评估指标

| 指标 | 定义 | 通过标准(MVP) |
|---|---|---|
| 记忆准确率 | 写入后立即测该批 QA 的正确率 | G1 ≥ 80%,与 G3 差距 ≤ 15pt |
| 选择性 | 用无关问题(通用常识题)测专家误激活率 | 误激活率 ≤ 5% |
| 旧记忆保持 | 顺序写入第 2、3、5 批后,重测第 1 批 | 准确率下降 ≤ 10pt(G2 预期显著下降) |
| 通用能力保持 | 写入前后跑 MMLU 子集(或 200 题常识 QA) | 下降 ≤ 2pt |

## 5. 环境适配(本机)

本机:Windows + i5-13490F + 32GB RAM + AMD RX 6800 XT(RDNA2/gfx1030,16GB)。

**torch-directml 调研结论(2026-07):**

- 最新版 `torch-directml 0.2.5.dev240914`(2024-09 发布,此后无更新),锁死 `torch==2.4.1` + `torchvision==0.19.1`;
- wheel 最高只到 **cp312**,本机现有 Python 3.13 不可用,需另装 Python 3.12 建 venv;
- DirectML 整体已被微软标记为 **maintenance mode**(只修安全问题,不再加功能),官方主推的替代品 Windows ML 面向推理,不适合本实验的训练需求;
- 生态兼容:需搭配 torch 2.4 时代的库(transformers ~4.44/4.45、peft ~0.12/0.13),锁版本使用;
- 使用方式:`import torch_directml; device = torch_directml.device()`,纯 PyTorch 代码基本无感;算子缺失会报错或回退 CPU;
- 结论:栈虽冻结,但 135M–1B 级 LoRA 训练在其能力范围内,值得试;失败则退回 CPU。

## 6. 实施步骤(MVP)

1. 搭环境:`.venv` + torch CPU + transformers + peft;
2. 写数据生成器:随机实体 + 事实模板 + 多种问法,生成 5 批虚构 QA,并人工抽查基座确实答不出;
3. 跑 G4/G3 基线,确认 G4≈0%、拿到 RAG 上限;
4. 实现 G1 写入:冻结基座训 LoRA 专家(数据=事实陈述句,loss=next-token);
5. 实现 G1 读取:隐向量路由 + 阈值门控;
6. 实现 G2 对照;
7. 跑顺序写入实验(5 批),输出四项指标表;
8. 判定 H1/H2/H3 是否成立,记录失败模式。

## 7. MVP 之后的进阶方向

- **surprise 写入门**:用输入的 perplexity 突增代替人工分批,自动决定"何时该记"(Titans 思路);
- **路由从隐向量检索升级为可学习 router**;
- **sleep-time 蒸馏**:定期把多个 LoRA 专家合并蒸馏成一个,控制专家数量增长;
- **干扰压力测试**:故意写入相互矛盾的虚构事实,观察门控能否隔离;
- 换更大基座(Qwen3-4B+),需 GPU 环境。

## 8. 主要风险

- **135M 模型本身能力太弱**:QA 格式可能都答不好,需要先验证基座在给定上下文时能做简单 QA(用 G3 RAG 组顺带验证);若不行,改用"陈述句补全准确率"作为记忆度量,而非自由问答;
- **隐向量路由区分度不足**:虚构事实彼此太像,余弦相似度分不开 → 备选:给每批事实加独特前缀 token,或用小型 embedding 模型(bge-small,CPU 可跑)做路由键;
- **LoRA 容量不足**:135M 模型单层维度小,50 条事实可能存不下 → 提高 rank,或减少每批事实数,记录容量曲线(这本身也是有价值的实验产出)。
